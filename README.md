# Python 逐行执行观察器

在网页上逐行观察本机可信 Python 代码的实际执行：Flask + 原生 HTML/CSS/JavaScript，
每次运行在独立子进程中进行（`bdb` 跟踪），先停在首条待执行行，可单步、继续或终止。

## 启动

```bash
docker compose up --build
```

访问地址：<http://localhost:8000>（端口 **8000**）

本地直接运行（可选）：`pip install -r requirements.txt && python app.py`，同样访问 8000 端口。

## 功能

- 编辑器最多接受 **80 行**代码，超出会被拒绝；页面内置赋值、函数调用、循环、异常四个示例。
- **运行**：在独立子进程中启动，自动停在第一条待执行行；运行期间源码只读。
- **单步**：停在下一条实际将执行的源码行（会进入函数调用、跟随循环逐次迭代）。
- **继续**：一直执行到结束或异常；**终止**：强制结束并回收子进程。
- 实时显示：下一条待执行行（高亮 + `→`）、当前局部变量的文本值、标准输出、异常堆栈。
- 暂停中或死循环（继续后）都可以随时查询状态或终止。
- **停顿回看**：运行过程中每次真实暂停都会定格一份快照（停顿序号、待执行行、
  局部变量文本、当时已保留的 stdout 及截断标记），快照此后不再变化；轮询状态与
  重复的单步/继续请求不会产生新记录。执行视图右上角“回看停顿”下拉框可选择任意
  历史停顿，页面随后进入历史模式：
  - 轮询照常更新实时状态（状态徽标、下拉列表），但不会切走所选记录；
  - 历史模式禁用“单步 / 继续”，“终止”仍作用于当前运行；
  - 点击“返回实时视图”（或在下拉框选回“实时视图”）会先拉取最新状态再启用控制，
    绝不会用历史停顿序号去推进执行；
  - 所选停顿被淘汰（只保留最近 100 次，旧记录淘汰后不重编号）时会提示并自动
    返回实时视图；
  - 运行结束、异常或被终止后历史仍可查看；只有**获准启动的新运行**才会清空，
    被拒绝的启动（如活动运行冲突）不清空。

## 并发与一致性规则

- 全站同一时刻只允许一个未结束的运行；结束后可修改代码再次运行。
- 控制请求（单步/继续/终止）携带 `run_id`；单步/继续还携带停顿序号 `pause_seq`。
- 同一次停顿最多接受一次控制请求：重复或过期请求返回 409 且不会推进执行。
- 前端只采纳与当前 `run_id` 匹配的状态响应，旧运行的迟到响应会被丢弃。
- 同一运行内重叠轮询的响应也按单调顺序采纳：状态（`pause_seq` 与状态阶段）和
  停顿历史（最大 `pause_seq`）都只许前进，较早轮询的迟到响应不改历史、选中项、
  实时状态、`pause_seq`、提示或按钮；有效终态立即停轮询并恢复编辑/重跑，不等
  在途的历史响应（详见下文“同一运行内的轮询乱序与终态锁页”）。

### 启动 / 终止 / 事件的协调（竞态修复）

启动一个运行分两步：先在服务端登记运行（分配 `run_id`、状态置为 running），再
`Popen` 创建 tracer 子进程。旧实现里这两步之间存在窗口：终止请求到来时虽然立刻把
状态改成 terminated 并返回成功，但 `proc` 还不存在、无法杀进程；随后原启动照常创建
子进程并开始喂代码。于是紧接着重跑可能留下两个存活子进程，旧 `run_id` 也再也终止
不了旧进程；此外，子进程被杀时管道里已缓冲的 pause/end 事件还会把 terminated 状态
改回 paused/running。

现在由一把条件变量统一协调启动、终止和事件读取，保证：

- **终止成功即无残留**：`/api/terminate` 返回 200 时，该运行的子进程已经死亡并被
  `wait()` 回收（无存活进程、无僵尸进程）。
- **启动期终止不丢**：终止在 `Popen` 尚未返回时到达会被登记；启动线程拿到进程句柄
  后自行杀掉并回收刚创建的子进程，未完成的启动不会再遗留进程。
- **旧进程回收前不接纳新运行**：`/api/run` 若发现上一个运行已终态但子进程尚未回收，
  会先等待回收完成再创建新子进程（等待超时返回 409“稍后重试”），两个子进程不可能
  并存。
- **终态粘滞、迟到事件丢弃**：事件只在该运行仍是“当前且活动”的运行时才被采用；
  terminated/finished/exception 之后到达的 pause、stdout、end 事件一律丢弃，状态
  不会从终态退回活动态；旧运行的事件也不会写入新运行。
- 子进程回收只在读取线程中进行一次（启动期终止时由启动线程回收），终止线程等待
  “已回收”信号而不是自己抢先 `wait()`，避免双重回收。
- 单运行冲突、过期控制请求仍返回 **409**；步进/继续的 `run_id`、`pause_seq` 与
  每次停顿至多一次的去重规则保持不变；`POST /api/run` 仍返回 `{run_id}`，
  `POST /api/terminate` 仍返回 `{ok, status}`，`GET /api/state` 结构不变。

### 重跑接纳：多个等待者抢槽（竞态修复）

复现：旧运行已结束（终态）但子进程尚未回收时，两个 `POST /api/run` 请求同时进入
等待。旧进程被回收后，先醒来的请求获准并登记新运行；若该运行很快报告终态（自然
结束、异常或被终止）而退出清理（读取线程的 `wait()` 回收）还没完成，另一个等待者
此时醒来，旧实现只检查“当前运行是否活动”，看到终态就放行——于是再登记一个运行
并创建子进程：两个存活子进程并存，且前一个运行的 `run_id` 立即失效（`CURRENT`
被顶替，旧标识无法再控制任何进程）。

修复后：`/api/run` 的接纳改为循环判断，每次从等待中醒来都重新读取**当时的**当前
运行：

- 当前运行是活动态 → 立即 409（活动运行占槽）；
- 当前运行是终态但子进程未回收 → 继续等它回收（与之前的等待共享同一截止时限，
  超时仍返回 409）；
- 当前运行是终态且已回收（或还没有任何运行）→ 才登记新运行并创建子进程。

等待期间绝不替换 `CURRENT`；子进程退出并被回收之前，绝不登记或创建下一运行，
因此任意时刻至多一个存活 tracer 子进程，等待中超时也不会提前顶替当前运行。

核对用测试（含可控线程交错：门控 `Popen` 复现“已登记未挂接”窗口、启动后立即重跑、
终止后灌入迟到事件、两个重跑请求同时等待回收且替代运行终态未回收、等待者醒来遇到
活动运行占槽、回收超时 409，以及正常暂停/步进/继续和死循环终止）：

```bash
pip install -r requirements.txt
python3 -m unittest test_races -v
```

其中 `test_stress_run_terminate_rerun` 用多线程在不加门控的真实交错下反复
运行→立即终止→立即重跑，并采样确认任意时刻至多一个存活 tracer 子进程、全部进程
最终被回收。`test_waiters_cannot_overtake_unreaped_replacement` 用门控的
`_wait_reaped` 精确复现上述抢槽窗口：两个等待中的重跑请求在“替代运行终态未回收”
时必须继续等待、不得创建第二个子进程，替代运行回收后恰好一个请求被接纳、另一个
收到 409。

### 重跑后的前端跨运行异步链（竞态修复）

复现：重跑后，上一轮遗留的两个并行轮询链可能仍在飞行中。其中一条轮询的历史查询
（`GET /api/pauses`）在新运行获准**之前**就已经拿到 200 响应（承载旧运行的停顿
列表），另一条轮询已经取得旧运行的**终态**；后一条先完成、用户启动的新运行获准
之后，前一条历史 200 才返回。旧实现只对 `/api/state` 校验了 `run_id`，但对
`/api/pauses` 的返回值没有任何归属校验，于是旧停顿被写进新运行的下拉框/视图；旧
终态随后又把新运行当作已结束处理——**停掉新轮询、解除源码只读、禁用终止按钮**。
同类问题还包括：旧的单步/继续（成功或 409）、旧终止的成功响应、以及双击运行时落败
那次 `/api/run` 的迟到 409，都会在新运行获准后改动新运行的提示、状态或触发多余轮询。

修复后，前端按“**只有获准启动的新运行才切换归属**”收敛整条异步链：

- **每一轮轮询自带代际**：进入 `poll()` 时捕获本轮的 `run_id`，在每一个 `await`
  （state 之后、pauses 之后）恢复时都重新校验；`/api/pauses` 的返回体还会再比对一次
  响应自带的 `run_id`——获准前已生成的旧 200 即使延迟到新运行之后才返回，也整体丢弃，
  绝不写入新运行的历史。
- **旧终态不得收尾**：只有仍属于当前运行、且是最新一轮的轮询才允许执行“停轮询 /
  解除只读 / 切换终止按钮”的收尾；旧轮询拿到的 finished/exception/terminated 一律
  只丢弃，不碰新运行的轮询、按钮、提示与源码只读状态。
- **旧控制响应静默丢弃**：单步/继续/终止在发请求时捕获所属 `run_id`，响应返回后若
  归属已变，其成功、失败（409）和收尾（`setTimeout(poll)`）都不再执行。
- **启动按获准切换**：仅当 `/api/run` 返回 200（服务端真正接纳）才更换 `run_id`、
  清空旧历史、切徽标为“运行中”、置源码只读并重启轮询；启动被拒绝（409）时保留当前
  回看与历史。并发的多次启动里，落败请求迟到的 409 即使在成功的 200 之后才返回，也
  不会再弹错误提示。
- 当前运行的正常轮询、历史选择（历史模式禁用单步/继续、终止仍可用、轮询更新徽标但不
  切走所选记录）、返回实时前先刷新、以及终止后回看历史，行为全部不变。

服务端配合的等价约定：所有控制与查询接口都改为“**在 `COND` 锁内决定结果与载荷、在锁
外序列化响应**”。这样一个已经构造好但被延迟返回的响应（测试用门控精确制造）绝不会
持锁阻塞新运行的接纳、状态轮询或子进程回收。接口字段与状态码不变：`GET /api/state`、
`GET /api/pauses?run_id=...`、`POST /api/run|step|continue|terminate` 的字段、成功载荷
与 409 约定全部保持原样；停顿去重（每次停顿至多一次步进/继续）、快照不可变、子进程只
回收一次等规则也不受影响。

可控交错的回归测试：

- 服务端 `DelayedResponseTests`（`python3 -m unittest test_races -v`）：用门控的
  `jsonify` 在**不持有条件变量**的前提下，把“已生成 200 的旧历史”“旧终态 state”
  “旧终止成功响应”“旧步进 409”“获准后才生成的过期 409”“被拒绝启动的 409”按报告
  中的精确顺序延迟到新运行获准之后返回，并验证：延迟响应仍只描述旧运行、新运行在
  此期间照常接纳/暂停/步进、任意停顿都不串台、`GET /api/state` 与各控制接口不被停放
  的响应阻塞。
- 前端 `test_frontend_races.js`（需 Node；已由 `python3 -m unittest test_races` 中的
  `FrontendAsyncChainTests` 自动调用，无 Node 时跳过）：用可控 `fetch` 响应顺序驱动
  **真实的** `static/app.js`，复现两条旧轮询并行、历史 200 先成后返、新运行获准的完整
  交错，并断言旧响应不改新运行的历史/状态/徽标/轮询/按钮/只读；同时覆盖迟到的旧步进、
  旧终止、迟到的启动 409，以及当前运行的轮询、历史回看、返回实时前刷新与终止。

### 同一运行内的轮询乱序与终态锁页（竞态修复）

跨运行的归属校验只回答“响应是否属于当前 `run_id`”，回答不了同一运行里**重叠
轮询**（400ms 定时轮询，与手动“返回实时视图”、单步/继续/终止后触发的 `poll`
叠加）的响应乱序。前端每轮轮询先发 `GET /api/state`、再发
`GET /api/pauses?run_id=...`，且这两个响应由不同 HTTP 连接返回，完成顺序完全
不保证。旧实现只在“终态收尾”时比较过轮询先后，因此有两类倒退：

- **较早轮询的旧状态/旧历史回退较晚轮询**：较早轮询先发 `pauses` 请求（此时
  只有停顿 #1），较晚轮询随后采纳了停顿 #2 并刷新了下拉框；用户选中**停顿 #2**
  后，较早轮询那份只含停顿 #1 的列表才返回——页面误判“停顿 #2 已被淘汰”，弹出
  淘汰提示并退出回看。同类地，较早轮询的旧 `/api/state` 迟到时会把实时
  `pause_seq`、徽标、待执行行和局部变量回退到更旧的停顿（之后单步就会带着过期
  序号发请求而被 409 拒绝）。
- **终态被在途的历史请求锁页**：结束/异常/终止的收尾旧实现位于 `await
  /api/pauses` **之后**，还要求自己必须是最新一轮轮询。历史响应慢（或始终不
  返回）时，后发的轮询不断在途，任何一轮都过不了“我仍是最新一轮”的检查，于是
  轮询不停、源码一直只读、“运行”按钮不可用、也无法重跑。

复现（慢响应/慢网络下会自然出现；测试用可控响应顺序精确制造）：

1. 运行一段至少有两个停顿的代码，等停顿 #1；
2. 让两轮轮询重叠：第一轮的 `/api/pauses` 请求在只有停顿 #1 时发出并**挂起**；
3. 第二轮轮询正常返回停顿 #2（`state.pause_seq=2`、历史含 #1、#2），在下拉框
   选中**停顿 #2**；
4. 放开第一轮挂起的 `pauses` 响应（200，只含停顿 #1）——修复前会误报“停顿 #2
   已淘汰”并返回实时；
5. 另让一轮较早轮询的 `/api/state`（停顿 #1）在较晚轮询采纳停顿 #3 之后返回
   ——修复前实时停顿退回 #1。
6. 终态锁页：一轮轮询的 `/api/state` 返回 `finished`，但其 `/api/pauses` 不
   返回；此后每 400ms 再来一轮同样持有终态的轮询——修复前页面一直只读、不能
   重跑。

修复后，前端对**同一运行**也按单调高水位采纳响应，较晚轮询一旦采纳，较早轮询
的迟到响应不得再改历史、选中项、实时状态、`pause_seq`、提示或按钮：

- **状态只前进**：以已展示的 `liveState` 为高水位，`pause_seq` 倒退、或同序号下
  状态阶段倒退（`running → paused`、终态 → 活动态）的 `/api/state` 整体丢弃，
  不再发后续历史请求、不渲染、不改 `pause_seq`。序号增大代表新停顿（即使阶段
  由 running 进入下一次 paused），照常采纳；
- **历史只增不减**：停顿集合只增不减（淘汰只在新增停顿的同一事件里发生，届时
  最大 `pause_seq` 严格增大），最大序号倒退的 `pauses` 列表必来自更旧的轮询，
  直接丢弃——选中的停顿不会再被旧列表“误淘汰”；最大序号相同视为同代，幂等
  重渲。真正被淘汰（已采纳更新的列表且仍不含所选项）时，淘汰提示与返回实时
  视图保持不变；
- **有效终态立即收尾**：采纳 `finished/exception/terminated` 后立即停轮询、
  解除源码只读、恢复“运行”按钮并禁用单步/继续，**不等待本轮 `/api/pauses`
  完成**；历史列表此后尽力刷新，响应慢或失败都不影响收尾，终态后历史仍可回看。
  收尾后在途的非终态迟到轮询也不得重渲活动视图或恢复只读。

跨运行隔离（`run_id` 归属校验、获准才切换）、真实淘汰提示、正常步进/继续/终止、
回看时禁用步进/继续且“返回实时视图”前先刷新等行为全部不变；`GET /api/state`、
`GET /api/pauses?run_id=...` 与各控制接口的字段、成功载荷、409 约定，以及停顿
去重与子进程回收规则均不变（本次只改前端与前端回归、文档）。

可控交错的前端回归（`node test_frontend_races.js`，也由
`python3 -m unittest test_races` 中的 `FrontendAsyncChainTests` 调用）在驱动
**真实的** `static/app.js` 的前提下新增覆盖：

- 较早轮询只含停顿 #1 的旧历史列表在选中停顿 #2 后才返回：不提示、不退出
  回看、不改选中项，返回实时后单步仍携带实时 `pause_seq`；
- 较早轮询的旧 `/api/state`（停顿 #1）在停顿 #3 采纳后返回：徽标、待执行行、
  按钮与实时 `pause_seq` 均不回退，且不再补发历史请求；同一 `pause_seq` 下
  `running` 之后迟到的 `paused` 快照也不能回退状态；
- 终态 `/api/state` 已采纳而本轮及后续多轮 `/api/pauses` 均不返回：轮询停止、
  源码恢复编辑、可重跑，历史仍可回看；此时获准的新运行不被旧运行挂起的历史
  响应影响；
- 正常收尾（终态后历史响应正常返回、终止后回看）与**真实**淘汰（更新的列表确实
  不含所选项）仍按原规则提示并返回实时。

## 限制

- 不支持交互式输入（`input()` 会得到 EOF 异常）与第三方包（仅标准库）。
- 标准输出保留最近约 100K 字符，超出部分截断。

## 接口

| 方法 | 路径 | 请求体 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/run` | `{code}` | 启动运行，返回 `{run_id}`；已有活动运行返回 409 |
| POST | `/api/step` | `{run_id, pause_seq}` | 单步；重复/过期返回 409 |
| POST | `/api/continue` | `{run_id, pause_seq}` | 继续至结束；重复/过期返回 409 |
| POST | `/api/terminate` | `{run_id}` | 终止并回收子进程；成功返回时子进程已死亡且被回收；运行不存在/已过期/已结束返回 409 |
| GET | `/api/state` | — | 当前运行完整状态（含 `run_id`、行号、局部变量、输出、异常） |
| GET | `/api/pauses?run_id=<id>` | — | 读取该运行最近 100 次停顿快照，按原 `pause_seq` 升序；错误或过期 `run_id` 返回 409 |

### 停顿回看 HTTP 示例

停顿快照只记录“已经经过的停顿”，只读、不会重新执行任何代码：

```bash
# 启动后单步几次，读取本次运行的停顿历史
curl -s http://localhost:8000/api/pauses?run_id=$RUN_ID | python3 -m json.tool
```

返回（旧记录淘汰后序号不重编号，可能从非 1 开始）：

```json
{
  "run_id": "9f2c…",
  "pauses": [
    {
      "pause_seq": 1,
      "current_line": 1,
      "locals": {},
      "stdout": "",
      "stdout_truncated": false
    },
    {
      "pause_seq": 2,
      "current_line": 2,
      "locals": {"x": "1"},
      "stdout": "",
      "stdout_truncated": false
    }
  ]
}
```

- 只返回最近 **100** 次停顿；超过后最旧的记录被淘汰，保留记录的 `pause_seq`
  不变。轮询 `/api/state`、重复/过期的单步与继续请求都不会新增记录。
- 运行已结束、异常或被终止时历史仍可读取；待新运行获准启动后旧 `run_id`
  立即过期，再用它查询会得到 **409**：

```bash
$ curl -i "http://localhost:8000/api/pauses?run_id=expired-id"
HTTP/1.1 409 CONFLICT
…
{"error":"运行不存在或已过期"}
```
